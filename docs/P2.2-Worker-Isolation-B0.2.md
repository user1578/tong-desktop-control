# P2.2 B0.2：LPAC 子进程诊断与隔离路线复评

状态：诊断完成；原生 Worker 安全修复和阶段 B 验收均未完成。基线为 `codex/p2-worker-isolation-review` 的 `ee0e698`。本轮只使用 `%TEMP%` 合成目录；没有运行真实 Codex 任务，没有修改在线 MCP、系统账户、服务或真实项目 ACL。

## 复现与直接原因

运行 `pwsh -NoProfile -File tests/Test-TongNativeWorkerSupervisor.ps1`。输出保存在 [stderr 管道第 1 次](evidence/B0.2-native-pipe-1.txt)、[stderr 管道第 2 次](evidence/B0.2-native-pipe-2.txt) 和 [合成文件句柄诊断](evidence/B0.2-native-file-stderr.txt)；归档时仅移除了四处行尾空格。合成子进程的原始 stderr 在测试目录内暂存，读取前 8 KiB、脱敏后写入日志，并删除原始文件；这次 stderr 共 647 字节，没有截断。日志没有打印环境变量或凭据。

最初把子进程 stderr 改为 Node 管道时，两次测试均停在 `spawn()` 调用内，没有“调用返回”事件；约 38 秒后由 Worker 任务超时路径结束。这个现象由诊断方式触发，其底层原因尚未定位，不能据此认定原始故障是管道故障。改用仅在合成项目内的文件句柄重定向后，原始退出码 1 稳定复现，事件为：调用开始 0 ms，`spawn` 事件 7 ms，`exit` 49 ms，`close` 50 ms。没有启动异常、stderr 读取异常或截断。

子进程 stderr 明确报告 `Error: EPERM: operation not permitted, lstat 'C:\'`，堆栈位于 Node 的 `realpathSync`、`Module._findPath`、`resolveMainPath` 和 `runMain`。子进程已经创建并启动，但在 Node 解析主脚本路径时因 `C:\` 文件访问被拒而退出；合成脚本的 `--child` 分支未执行，因此没有 `child.json`。主 Worker 的启动命令带有 `--preserve-symlinks-main`，合成子进程命令没有该参数。这解释了两者行为差异，但本轮没有改变子进程命令或 LPAC 权限来追求通过。IPC 请求已到达主 Worker；原始退出码 1 的直接原因不是 Worker 请求管道读取失败。

这次运行到达 `tests/Run-TongNativeWorkerSupervisor.mjs` 第 53 行子进程退出码断言，预期 0、实际 1。此前的项目内读/写/删、Node/Git/Python/Codex `--version` 退出码 0、项目外 `Everyone`、`Users`、`Authenticated Users`、All Application Packages、All Restricted Application Packages 的读/写/删拒绝、junction 拒绝及敏感环境标记缺失断言均已执行并通过。日志摘要中后两组字段仍为空，是摘要字段名与探针键名不匹配；负向断言实际位于子进程断言之前。Supervisor 持锁期间，并发 ACL journal 写入被拒绝且合成项目 DACL 未变。

尚未通过或未到达：子进程写入 `child.json`、子进程项目内/外权限、Job 后代清理、取消与超时清理、伪造 HMAC、恶意命名管道 peer、ACL 崩溃恢复及外部 DACL 变更冲突、逐任务 SID 隔离、独立账户验收、真实 Codex 任务和完整回归。`--version` 成功只证明版本命令可运行。

## 路线比较

| 维度 | 继续 Windows 原生 Worker | 独立虚拟机 Worker |
| --- | --- | --- |
| 安全边界 | 与宿主共享 Windows 内核，依赖账户、LPAC、文件 ACL、管道和 Job 的组合；当前任务 SID 未参与访问检查，AppContainer 身份也不是每任务唯一。 | 客体拥有独立操作系统和虚拟磁盘；在禁用宿主共享、限制网络及传输通道后，项目和认证数据的边界更清晰。仍需维护虚拟化平台、客体和传输端。 |
| 开发成本 | 可复用现有 Supervisor；解决这个 Node 入口错误的范围较小。但逐任务权限、运行时依赖、子进程和 ACL 恢复仍未闭环，后续成本不确定。 | 初期需要镜像、任务协议、项目副本、结果回传、网络策略和更新机制；CPU、内存、磁盘成本更高。 |
| 认证 | 需要独立 Windows 账户与服务身份，并在该身份下单独认证 Codex；不能复制主用户认证。 | 每个持久 Worker 客体使用自己的身份和认证存储；任务副本与凭据分离，不把宿主 token、Cookie 或 `CODEX_HOME` 放入镜像或项目包。 |
| 项目数据 | 临时 ACL 让 Worker 直接访问宿主项目，日志恢复和并发冲突都影响宿主文件。 | Broker 只从已注册根创建受控快照，客体在虚拟磁盘上操作；结果以补丁和受限产物清单回传，宿主校验后再应用。 |
| 网络 | 与宿主网络环境紧密耦合，还需单独处理外传和本机服务访问。 | 可以为客体设计专用出站策略，但不能把默认 NAT 当成隔离证明；某些实现允许客体访问宿主 loopback 服务。 |
| 取消任务 | Job Object 机制已存在，但后代清理断言尚未通过；ACL 只能在进程退出后安全恢复。 | 先终止客体内进程组，超时后关闭并丢弃任务客体/工作盘；回传部分日志，停止接受该任务结果。 |
| 多 Agent | 当前管道服务与 ACL journal 仍围绕共享身份和宿主目录，扩展并行任务需解决任务间权限和 DACL 竞争。 | 每个 Agent 或信任域使用独立客体与项目副本，隔离更直观；资源开销与补丁冲突处理随并发增长。 |

**建议：后续安全路线转向独立虚拟机 Worker 的受控原型。** 这是一项路线决策，不是虚拟机安全验收。原生路线的 Node 入口错误已有直接原因，但修正它仍不能补齐逐任务 SID、Job 后代清理和独立账户证据。继续为原生模型增加例外与 ACL 授权的收益小于继续承担的边界复杂度。保留现有负向测试作为以后任何路线的准入门槛。

本机是 Windows 11 Home（build 26200），微软文档说明该版本不能安装 Hyper-V 角色；选择本地第三方虚拟化或远端虚拟机都需要单独评估资源、安装权限和网络。Oracle 文档明确指出共享文件夹会把宿主文件暴露给客体，且默认 NAT 可访问宿主 loopback，因此两者都不能作为安全默认值。[Hyper-V 安装要求](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/install-hyper-v?pivots=windows)、[VirtualBox 安全指南](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/Security.html)、[VirtualBox NAT 说明](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/networkingdetails.html)。本轮没有安装或配置虚拟化软件。

## 虚拟机路线的最低边界

1. **宿主文件：**默认禁止挂载宿主 `C:\`、`D:\`、用户目录和任何私人文件共享；禁用共享剪贴板、拖放、USB 直通及自动共享文件夹。传输接口只能处理明确注册的单个项目副本。
2. **项目输入：**宿主 Broker 核对授权项目根，枚举受控文件清单和大小上限；拒绝越界路径、reparse point、指向根外的链接及默认排除的凭据文件。把文件哈希、任务 ID、授权范围与副本一起通过已认证的加密通道发送到客体临时工作盘。需要的未跟踪文件由明确清单加入，不能自动打包整个私人目录。
3. **结果输出：**客体返回带哈希的补丁、产物清单及脱敏日志；宿主只接受清单内相对路径，复核路径与大小，再由现有任务授权流程决定是否应用。客体没有直接写宿主项目的通道。失败或取消时不自动应用部分结果。
4. **认证与网络：**客体使用独立的 Codex 认证和最小出站访问。任务通道使用双向身份校验、每任务密钥和超时；除明确的专用任务通道地址外，客体不得访问宿主 Gateway/DevSpace loopback、家庭局域网或私人网段。选定虚拟化平台后必须实际验证网络策略，不能仅凭 NAT 默认行为判断。
5. **取消与并发：**先终止客体任务进程组，再以关闭/丢弃客体作为最后清理手段。多 Agent 使用独立客体或独立信任域工作盘，宿主集中调度并检测补丁冲突；不共享可写项目盘或认证目录。

这些条件仍需独立设计和合成验收。本轮不创建虚拟机、不切换在线 P2.1 MCP、不启用真实 Agent 执行，也不自动进入下一阶段。

## 遗留合成目录

[精确目录清单](evidence/B0.2-legacy-synthetic-roots.txt)记录了 20 个遗留目录的完整路径和本地创建时间。每个目录都位于 `%TEMP%`，名称符合合成测试格式，含 `original-acl.txt`，且 `bin/policy.json` 中 `syntheticOnly=true`、`syntheticRoot` 与该目录精确一致；据此归因于 `tests/Test-TongNativeWorkerSupervisor.ps1` 的旧失败运行。本轮三次测试新建的目录由测试 `finally` 清理，旧目录未删除。

将来若清理，应先逐一复核清单中的绝对路径、合成策略与文件身份，确认没有活跃进程或未处理的 `*.acl.json` / `*.pending` 记录，并核对项目 DACL 与日志备份。出现身份或 DACL 冲突时保留目录供人工处理。仅在用户批准精确目标且工具允许后，对这些已核对的临时目录执行清理；不使用通配符、不绕过工具保护、不触碰真实项目。
